# Agent evidence and security boundaries

Evidence records bind a generated evidence ID to an actual ToolExecutor execution ID, name/version, source resource reference, collection time and schema-validation status. Lists preserve returned ticket/transaction identifiers; policy lists preserve policy IDs and versions. Findings cite only collected evidence IDs. Empty successful lists are recorded as empty observations, never fabricated records. Missing transaction or policy evidence prevents completion. A ticket absent from the bounded customer list stops for review; a full 20-ticket list is conservatively considered potentially truncated.

The orchestrator holds bounded validated tool outputs internally. Summaries expose structured status, block reason, evidence version, ticket category/duplicate reference, counts and payment statuses, not arbitrary ticket/policy prose. Source schema validation proves shape and authorized retrieval, not factual truth. Ledger samples and historical policy versions remain incomplete evidence. No account is certified eligible for reactivation, even if billing appears resolved.

Planner calls receive deep copies, so mutating a planner observation cannot rewrite collected evidence. Provider interpretation is compared with a backend deterministic structured-field classification; recommendation text must match the bounded safe advisory mapping. The UI separately labels retrieval evidence, interpretation and advisory recommendations. It displays only actual returned states and escaped text, without fake execution animations.

Authorization derives from the existing authenticated session. Each tool revalidates it, enforces current investigation permission and its own read permission, checks strict arguments and uses tenant-scoped read-only queries. Planner output cannot invoke write actions or circumvent ToolExecutor. Invocation arguments may not substitute a foreign customer, ticket or account. No unrestricted HTTP/database/code/shell tool exists. Retrieved prompt injection cannot select tools or alter permissions.

Tool metadata is persisted by Phase 2 without raw goals/arguments/customer results. Phase 4 persists investigation goals/context, states, allowlisted evidence, events and versioned checkpoints in PostgreSQL; see [persistence](INVESTIGATION_PERSISTENCE.md) and [recovery guarantees](RECOVERY.md). Checkpoints omit duplicated source prose and session secrets. Result lookup requires tenant, actor and permission. RLS and least-privilege deployment credentials remain deferred; the development DB owner can alter audit records. No production readiness, real-provider robustness or immutable ledger is claimed.

Tool calls use separate authorized read snapshots. Evidence can change between calls; collection timestamps and versions aid review but do not establish an atomic business snapshot. Any later write workflow must independently revalidate resource state and authorization.
